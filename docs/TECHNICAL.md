# HSE Guard — Technical Architecture

## 1. فناوری‌ها و محدودیت‌ها

- Backend: Python + Django + Django REST Framework.
- Frontend: React + TypeScript + Vite.
- Database: SQLite، فایل `db.sqlite3`.
- API: REST/JSON، پیشوند `/api/v1/`.
- UI: فارسی، RTL، واکنش‌گرا.
- آزمون Backend: ابزارهای آزمون Django؛ آزمون Frontend متناسب با ابزارهای انتخاب‌شده پروژه.
- پیکربندی: متغیرهای محیطی و فایل‌های نمونه.
- اجرای محلی و استقرار: بدون Docker.

**ممنوع:** Docker، Docker Compose و Dockerfile. بدون تصمیم صریح پروژه، فناوری‌های اصلی یا SQLite را تغییر نده.

ابتدا مخزن موجود را بررسی کن؛ اگر کد یا ساختاری از قبل وجود دارد، آن را حفظ و تکمیل کن. ساختار زیر الگوی پیشنهادی است، نه مجوز بازنویسی بی‌دلیل پروژه.

## 3. معماری Backend

هر اپلیکیشن فقط مسئولیت مشخص خود را داشته باشد. فایل‌های رایج:

- `models.py`: مدل‌ها و ارتباطات داده.
- `serializers.py`: اعتبارسنجی و تبدیل داده‌های API.
- `views.py`: مدیریت درخواست و پاسخ.
- `urls.py`: مسیرهای API.
- `permissions.py`: کنترل دسترسی.
- `services.py`: منطق تجاری و عملیات چندمرحله‌ای.
- `selectors.py`: پرس‌وجوهای خواندن پیچیده، در صورت نیاز.
- `tests.py` یا پوشه `tests/`: آزمون‌ها.
- `migrations/`: تغییرات نسخه‌بندی‌شده پایگاه داده.

تمام فایل‌ها در همه اپلیکیشن‌ها اجباری نیستند. از لایه‌ها، کلاس‌ها، abstractionها و وابستگی‌های غیرضروری اجتناب کن.

مسئولیت اپلیکیشن‌ها:

- `accounts`: کاربر، احراز هویت و نقش‌ها.
- `organizations`: سازمان و عضویت کاربران.
- `workplaces`: سایت، کارگاه، محل، تجهیز و فعالیت.
- `knowledge_base`: منابع و اسناد مرجع.
- `risk_assessments`: خطرها، ارزیابی‌ها و محاسبات ریسک.
- `checklists`: تعریف و نسخه‌بندی چک‌لیست.
- `inspections`: اجرای بازرسی و پاسخ‌ها.
- `findings`: مشاهدات و عدم‌انطباق‌ها.
- `capa`: اقدامات اصلاحی و پیشگیرانه.
- `notifications`: اعلان‌های درون‌سامانه‌ای.
- `ai_assistant`: سرویس مستقل پیشنهادهای هوش مصنوعی.
- `auditlog`: رخدادهای قابل حسابرسی.

در صورت نیاز، عملیات چندمدلی را در serviceهای مشخص و تراکنش‌های پایگاه داده اجرا کن. منطق حیاتی را در signalهای پنهان پراکنده نکن.

## 4. معماری Frontend

- `app/`: راه‌اندازی برنامه و تنظیمات سطح بالا.
- `components/`: اجزای عمومی UI.
- `features/`: صفحات، اجزا و منطق هر قابلیت.
- `layouts/`: چیدمان پنل و منو.
- `services/`: ارتباط با API.
- `hooks/`: هوک‌های مشترک.
- `types/`: نوع‌های TypeScript.
- `utils/`: توابع عمومی.
- `styles/`: استایل‌ها و تنظیمات RTL.

هر Feature تا حد امکان اجزای اختصاصی خود را نگه دارد. منطق محاسبات حساس، مجوزها و تصمیم‌های تجاری نباید فقط در Frontend اجرا شوند.

رابط کاربری باید خطا، بارگذاری، داده خالی، موفقیت عملیات و خطاهای اعتبارسنجی را به‌شکل روشن مدیریت کند.

## 5. مدل داده مفهومی

مدل‌ها و نام نهایی فیلدها را پس از بررسی مخزن و طراحی جزئیات انتخاب کن. موجودیت‌های اصلی:

- `User`: حساب کاربر و وضعیت فعال‌بودن.
- `Organization`: سازمان.
- `Membership` یا ساختار معادل: ارتباط کاربر، سازمان و نقش.
- `Workplace`: محل کاری و ارتباط سلسله‌مراتبی آن.
- `KnowledgeSource`: منبع مرجع و فراداده اعتبار.
- `Hazard`: خطر شناسایی‌شده.
- `RiskAssessment`: احتمال، شدت، امتیاز، طبقه، کنترل‌ها و وضعیت تأیید.
- `Checklist`: اطلاعات اصلی چک‌لیست.
- `ChecklistVersion`: نسخه ثابت چک‌لیست.
- `ChecklistItem`: آیتم نسخه مشخص.
- `Inspection`: بازرسی، محل، بازرس، نسخه چک‌لیست و وضعیت.
- `InspectionResponse`: پاسخ به آیتم بازرسی.
- `Finding`: مشاهده یا عدم‌انطباق.
- `Evidence`: اطلاعات فایل یا مدرک مرتبط.
- `CorrectiveAction`: اقدام، مسئول، مهلت، وضعیت و نتیجه تأیید.
- `Notification`: گیرنده، محتوا، زمان و وضعیت خواندن.
- `AuditEvent`: عامل، زمان، نوع عملیات و موجودیت مرتبط.
- `Equipment`: دارایی HSE با کد یکتا در سازمان، دسته، وضعیت، محل، مشخصات و کالیبراسیون الزامی.
- `MaintenancePlan`: برنامه نگهداری با تناوب ۱ تا ۳۶۵۰ روز، مسئول و موعد بعدی.
- `MaintenanceWorkOrder`: دستورکار پیشگیرانه/اصلاحی با گردش وضعیت و حفظ نتیجه سرویس.
- `CalibrationRecord`: تاریخچه کالیبراسیون با نتیجه قبول/ناموفق، سررسید و ارجاع مدرک.
- `AIRequest` یا ساختار معادل: وضعیت درخواست هوش مصنوعی در صورت نیاز.

قواعد داده:

1. کلیدهای خارجی و محدودیت‌های لازم را تعریف کن.
2. تاریخ ایجاد و تغییر را در موجودیت‌های مناسب ثبت کن.
3. داده‌های سازمانی را در تمام پرس‌وجوها محدود کن.
4. از حذف آبشاری خطرناک برای سوابق بازرسی، یافته‌ها، CAPA و حسابرسی اجتناب کن.
5. برای سوابق مهم، غیرفعال‌سازی یا بایگانی را به حذف دائمی ترجیح بده.
6. برای وضعیت‌ها از مقادیر کنترل‌شده استفاده کن.
7. یکتایی و ایندکس‌ها را بر اساس نیاز واقعی تعریف کن.
8. تمام تغییرات ساختار را با Django Migrations اعمال کن.
9. مدل کاربر سفارشی را در صورت شروع پروژه از ابتدا پیش از نخستین Migration تعریف کن؛ اگر پروژه موجود است، قبل از تغییر مدل کاربر، مهاجرت‌ها و وابستگی‌ها را بررسی کن.
10. فایل SQLite و داده‌های واقعی نباید وارد Git شوند.

## 6. سازمان و مجوزها

تمام عملیات خواندن، ایجاد، تغییر و حذف باید هم هویت و هم مجوز کاربر را بررسی کنند.

- سازمان کاربر را از داده احراز هویت‌شده و عضویت معتبر تعیین کن؛ به `organization_id` ارسالی کلاینت اعتماد نکن.
- فهرست‌ها را از ابتدا به محدوده سازمان مجاز محدود کن.
- دسترسی مستقیم به شناسه رکورد دیگر سازمان باید رد شود.
- تغییر مالکیت سازمانی باید به‌شدت محدود یا ممنوع باشد.
- نقش‌های مدیریتی نیز باید در محدوده مجاز خود عمل کنند.
- عملیات حساس باید در Audit Log ثبت شوند.
- دسترسی‌های غیرمجاز باید با آزمون‌های صریح پوشش داده شوند.

پیشوند: `/api/v1/`

مسیرهای پیشنهادی:

```text

/api/v1/checklists/

/api/v1/findings/
/api/v1/capa/
/api/v1/notifications/
/api/v1/audit-logs/
/api/v1/assets/equipment/
/api/v1/assets/equipment/<pk>/status/
/api/v1/assets/equipment/stats/
/api/v1/assets/maintenance-plans/
/api/v1/assets/maintenance-work-orders/
/api/v1/assets/calibrations/
/api/v1/reports/export/assets/
```

این‌ها مسیرهای منطقی پیشنهادی‌اند؛ مسیر نهایی باید با API واقعی هماهنگ باشد.

قواعد API:

- استفاده از HTTP status code مناسب.
- اعتبارسنجی ورودی در Serializer و در صورت لزوم service.
- خروجی JSON با ساختار یکنواخت.
- صفحه‌بندی فهرست‌های بزرگ.
- فیلتر و مرتب‌سازی محدود به فیلدهای مجاز.
- جلوگیری از افشای traceback یا جزئیات حساس در پاسخ.
- مجوز مستقل برای هر عملیات حساس.
- مستندسازی قرارداد API و نمونه خطاها.
- Frontend فقط از API استفاده کند و مستقیماً پایگاه داده را دست‌کاری نکند.

## 8. احراز هویت

روش احراز هویت را پس از بررسی نیاز و محیط استقرار انتخاب کن و در کل پروژه یکپارچه نگه دار.

اگر از Session استفاده می‌شود، CSRF، کوکی‌ها و CORS را درست تنظیم کن. اگر از Token/JWT استفاده می‌شود، انقضا، اعتبارسنجی، ابطال و محل نگهداری امن توکن را بررسی کن. توکن یا رمز نباید در URL یا گزارش‌ها ثبت شود.

هم‌زمان چند روش احراز هویت را بدون نیاز روشن اضافه نکن.

## 9. محاسبه ریسک

یک تابع یا service مشخص و قابل آزمون ایجاد کن.

ورودی‌ها:
- احتمال وقوع در محدوده تعریف‌شده.
- شدت پیامد در محدوده تعریف‌شده.

خروجی:
- امتیاز محاسبه‌شده.
- طبقه ریسک طبق تنظیمات فعال.

فرمول پایه:

`score = likelihood × severity`

آستانه‌ها و مقیاس‌ها باید مستند باشند و بدون مبنای مصوب به‌عنوان استاندارد قطعی ایمنی معرفی نشوند. Frontend فقط داده را ارسال و نتیجه سرور را نمایش دهد. آزمون مقادیر مرزی و ورودی نامعتبر الزامی است.

## 10. هوش مصنوعی

فراخوانی مدل را در لایه‌ای مستقل نگه دار:

`API → Input Validation → Context Preparation → Provider Adapter → Response Validation`

- کلید API فقط در Backend و متغیر محیطی باشد.
- ورودی و خروجی اعتبارسنجی شوند.
- خروجی به‌صورت پیشنهاد نمایش داده شود.
- منبع جعلی یا الزام قانونی ساختگی تولید نشود.
- ارسال داده محرمانه به سرویس خارجی مطابق سیاست سازمان باشد.
- timeout و خطا مدیریت شوند.
- نبود سرویس AI، بازرسی، ریسک و CAPA را مختل نکند.
- از ذخیره غیرضروری promptها یا اطلاعات حساس خودداری شود.
- سرویس و مدل انتخابی باید از طریق تنظیمات قابل تغییر باشند.

## 11. فایل‌ها

فایل‌های شواهد باید خصوصی و تحت کنترل مجوز رکورد مرتبط باشند.

- نوع و اندازه فایل را بررسی کن.
- نام ذخیره‌سازی امن داشته باش.
- به پسوند فایل به‌تنهایی اعتماد نکن.
- مسیر فایل را از ورودی کاربر به‌صورت خام نساز.
- فایل خصوصی را در مسیر عمومی قابل دسترسی بدون مجوز قرار نده.
- سیاست پشتیبان‌گیری از فایل‌ها را همراه SQLite در نظر بگیر.

## 12. تنظیمات و اسرار

نمونه `.env.example` برای توسعه:

```dotenv
DJANGO_SECRET_KEY=replace-me
DJANGO_DEBUG=True
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1
DATABASE_PATH=db.sqlite3
FRONTEND_ORIGIN=http://localhost:5173
AI_PROVIDER=
AI_API_KEY=
```

نام متغیرها را با تنظیمات واقعی پروژه هماهنگ کن.

- فایل `.env` واقعی را به Git اضافه نکن.
- مقادیر نمونه نباید اسرار واقعی باشند.
- در محیط عملیاتی `DEBUG=False`.
- `ALLOWED_HOSTS` و CORS فقط به دامنه‌های موردنیاز محدود باشند.
- HTTPS و تنظیمات امن کوکی متناسب با روش احراز هویت فعال باشند.
- از ثبت رمز، توکن و کلیدها در لاگ‌ها جلوگیری کن.

## 13. SQLite و پشتیبان‌گیری

SQLite پایگاه داده نسخه فعلی است؛ بدون تصمیم صریح آن را عوض نکن.

- تراکنش‌های نوشتن را کوتاه نگه دار.
- عملیات طولانی را داخل تراکنش نگه ندار.
- از Migration برای تغییر ساختار استفاده کن.
- نسخه پشتیبان سازگار با SQLite تهیه کن و بازیابی آن را آزمایش کن.
- فایل پایگاه داده را در Git ثبت نکن.
- فایل‌های رسانه‌ای مهم را نیز در پشتیبان‌گیری لحاظ کن.
- محدودیت‌های هم‌زمانی نوشتن SQLite را در استقرار در نظر بگیر.
- پایگاه داده را روی فضای ذخیره‌سازی محلی مناسب نگه دار.

## 14. آزمون‌های الزامی

Backend:
- مدل‌ها و اعتبارسنجی.
- APIهای موفق و ناموفق.
- احراز هویت و مجوزها.
- دسترسی میان‌سازمانی.
- محاسبه ریسک و مقادیر مرزی.
- گردش کار بازرسی.
- ارتباط یافته و CAPA.
- مسئول، مهلت و تأیید اقدامات.
- دسترسی فایل‌ها.
- ثبت رخدادهای حساس.
- جداسازی سازمانی و قواعد وضعیت تجهیز، موعد نگهداری و کالیبراسیون.
- محاسبه `next_due_date = completed_date + interval_days` و جلوگیری از آماده‌سازی تجهیز ناایمن.

Frontend:
- فرم‌ها و خطاهای اعتبارسنجی.
- بارگذاری، خطا و فهرست خالی.
- نمایش وضعیت عملیات.
- RTL و صفحات واکنش‌گرا.
- رفتار رابط بر اساس نقش.

قبل از اعلام اتمام، آزمون‌های موجود و مرتبط را اجرا کن. اگر آزمونی اجرا نشد، دلیل و وضعیت آن را صریح اعلام کن.

## 15. اجرای محلی بدون Docker

PowerShell، از ریشه مخزن:

```powershell
cd backend
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

در ترمینال دوم:

```powershell
cd frontend
npm install
npm run dev
```

این دستورات مشروط به وجود فایل‌ها و تنظیمات متناظر هستند. وابستگی‌ها را بر اساس مخزن واقعی نصب کن و از ایجاد فایل‌های ساختگی برای تطبیق با این مثال اجتناب کن.

## 16. استقرار و عملیات

پیش از استقرار:

1. متغیرهای محیط عملیاتی را تنظیم کن.
2. `DEBUG=False` و Hostهای مجاز را بررسی کن.
3. Migrationها را بازبینی و اجرا کن.
4. تنظیمات Static و Media را مطابق میزبان تنظیم کن.
5. مجوز فایل SQLite و فایل‌های خصوصی را بررسی کن.
6. نسخه پشتیبان تهیه کن.
7. آزمون‌های حیاتی را اجرا کن.
8. اتصال Frontend به API را بررسی کن.
9. ثبت خطا و روش بازیابی را بررسی کن.

روش استقرار نهایی باید با امکانات واقعی میزبان هماهنگ باشد؛ Docker در هیچ مرحله‌ای استفاده نشود.

## 17. ماژول دارایی، نگهداری و کالیبراسیون (فاز ۹)

- اپ `apps.assets` با مدل‌های `Equipment`, `MaintenancePlan`, `MaintenanceWorkOrder`, `CalibrationRecord`.
- کد تجهیز در هر سازمان یکتا و بدون حساسیت به حروف بررسی می‌شود.
- وضعیت‌ها: `ready`, `under_maintenance`, `out_of_service`, `retired`؛ تغییر وضعیت فقط از endpoint اختصاصی و سرویس کنترل‌شده.
- کالیبراسیون الزامی بدون آخرین رکورد معتبر مانع `ready` است؛ نتیجه ناموفق تجهیز را `out_of_service` می‌کند.
- کار اصلاحی باز/در حال اجرا مانع `ready` است؛ کار پیشگیرانه آینده مانع نیست.
- ارتباط اختیاری با Incident، Inspection و NonConformity و M2M با Hazard/Permit؛ CAPA از مسیر NonConformity.
- Audit رویدادهای ایجاد/تغییر وضعیت/برنامه/دستورکار/کالیبراسیون و اعلان تخصیص و شکست کالیبراسیون.
- UI فارسی/RTL با KPI، جست‌وجو، فیلتر، فرم‌ها و حالت‌های loading/error/empty.
- گزارش CSV تجهیزات شامل وضعیت، کالیبراسیون، سررسیدها، موعد نگهداری و دستورکار باز در صفحه گزارش‌ها.
- داده دموی سنتتیک idempotent با حفظ رکوردهای واقعی و رمزهای موجود؛ بازنشانی رمز فقط با گزینه صریح.

محدودیت‌ها: محاسبه سررسید lazy است و scheduler روزانه ندارد؛ آپلود مدرک کالیبراسیون وجود ندارد؛ SQLite برای MVP است.

## 19. ماژول مدیریت کارکنان، صلاحیت و تجهیزات حفاظت فردی (فاز ۱۰)

- اپلیکیشن `apps.workforce` شامل مدل‌های `Employee`, `TrainingCourse`, `TrainingSession`, `TrainingAttendance`, `Competency`, `EmployeeCompetency`, `PPEItem`, `PPEStock`, `PPEAssignment`, `PPEAssignmentEvent`.
- ارتباط پرسنل با مجوزهای کار پرخطر (`permits.PermitTypeCompetencyRequirement`)؛ ارزیابی خودکار صلاحیت قبل از صدور یا فعال‌سازی مجوز کار.
- پایش تاریخ انقضای صلاحیت‌ها و هشدار ۳۰ روزه پیش از سررسید.
- مدیریت چرخه عمر PPE (تحویل، تعویض، انقضا، اسقاط) و هشدار موجودی زیر حد نصاب.
- ایزولاسیون کامل داده‌ها بر پایه سازمان و ثبت ردپای حسابرسی رویدادها در `apps.auditlog`.

## ۲۰. تکمیل محصول، سیستم طراحی و معماری رابط کاربری (پیش از فاز ۱۱)

- **سیستم طراحی (Design System) مبتنی بر توکن‌های CSS:** پالت رنگی استاندارد، عمق و سایه‌ها (`--shadow-*`)، شعاع گوشه‌ها (`--radius-*`) و تایپوگرافی فارسی.
- **موتور پوسته (Theme Engine):** پشتیبانی از سه حالت `light`، `dark` و `system` با ذخیره‌سازی در `localStorage` و سنکرون با `prefers-color-scheme`.
- **معماری ناوبری:** نوار کناری (Sidebar) ساختاریافته در ۵ گروه عملیاتی، حالت جمع‌شونده در دسکتاپ و کشویی در موبایل؛ هدر تعاملی با مسیر راهنما (Breadcrumbs)، زنگوله اعلان‌ها و پروفایل کاربری.
- **داشبورد مدیریتی یکپارچه:** تجمیع شاخص‌های عملیاتی از ۵ ماژول اصلی و برجسته‌سازی هشدارهای سررسید گذشته با نشانگرهای بصری.
- **تکمیل گزارش‌ها:** پیاده‌سازی خروجی‌های استاندارد CSV برای ماژول‌های `permits` و `incidents`.
- **تضمین کیفیت:** ۲۱۱ آزمون بک‌اند جنگو، ۴۸ آزمون فرانت‌اند با Vitest و بیلد پروداکشن پاک با TypeScript.
